# 测试记录

所有测试都由没看过开发过程的独立 agent 运行：只给它 `SKILL.md`、`references/` 和用例输入。另外用了一篇未公开的真实语音稿（约 30 处识别错误、三个话题抢位置），它只用于测试，不放进仓库。

## 通用检查项

- [ ] 没有改写作者的句子，只调顺序、合并、修识别错误
- [ ] 没有编造经历、数据、例子，缺的地方用【】提示
- [ ] 没有把“吧”“大概”“我觉得”改成确定语气
- [ ] 没有破折号，成稿里没有金句收尾、加粗和小标题
- [ ] 第一步之后停下等作者，不擅自出成稿

## 1. 和不装 Skill 对比（盲评）

同样的输入，一份装 Skill，一份是普通 AI 收到“帮我整理一下这篇稿子”。第三个 agent 不知道哪份是哪份，按 5 项各打 1 到 5 分：中心与意图、问题深度、保留原话、识别错误处理、实际帮助。

| 用例 | 装 Skill | 不装 Skill |
|---|---|---|
| 真实语音稿（未公开） | 24 | 13 |
| case-work 打工经历 | 23 | 17 |
| case-ad 商单 | 24 | 19 |

评审总结的差别：
- 装 Skill 的版本稳定地找到了不装时漏掉的问题：
  - 真实语音稿里“普通人接不住我”和“不要把别人当傻子”的矛盾
  - 打工稿里“店长救了我”和“客人逼我开口”的归因冲突，以及“我差点超了”等于公开承认差点违反签证工时规定的风险
  - 商单稿里外刊来源要核实，原话里的“吧”不能改成肯定
- 不装 Skill 的版本会悄悄改词、删口头禅，偶尔替作者写半句。
- 装 Skill 的代价是要多来回一轮，拿不到立刻能用的稿子。

文件：`case-work.with-skill.md`、`case-work.baseline.md`、`case-ad.output.md`、`case-ad.baseline.md`

## 2. 多轮对话

第一步之后模拟作者回复，看第二步是否越界。

- **case-ad**：作者回复了一个真实的记单词例子和数据来源。成稿只用了作者这轮的原话，产品名落在 15 秒内，竞品名去掉，字数和秒数正确，还提醒核实外刊来源。文件：`case-ad.turn2.md`
- **真实语音稿**：作者说“具体例子暂时想不起来”。成稿没有编例子，用【】留了可选的提示；没猜出来的词在稿子里占位，并列出待确认。

## 3. 稳定性

同一篇真实语音稿独立运行 4 次。4 次都：
- 判断出三条线在抢位置，建议同一条当主线
- 建议把文学那段拿出去单独做
- 抓到同一个前后矛盾，并提醒“普通人”那句可能被骂
- 把识别错误分成“直接改”和“拿不准”两组

中心句的措辞略有不同，但指向同一个意思。

## 4. 启用测试

模拟 5 个技能并存（本 Skill、humanizer-zh、公众号写作、翻译、起标题），给 12 条请求，看路由选哪个。

- **第一轮**（`trigger-round1.md`）：
  - “品牌方要 15 秒内提到产品，帮我看看这个口播稿”没能稳定启用
  - “这篇怎么改”太宽，会抢走去 AI 味和查错别字的请求
- **改进后**：12 条全部路由正确，包括“把我说的这段变成能拍的稿子”和“哪里可以删”。

## 单项用例

- `case-ad.txt`：商单，品牌要求 90 秒内、15 秒内提到产品、不提竞品
- `case-skip-discussion.txt`：作者要求跳过讨论
- `case-work.txt`：打工经历，原稿较顺，藏着归因矛盾和签证风险

## 测试后的修改记录

第一轮：
- 待确认词分成“直接改的”和“拿不准的”两组
- 补上作者要求跳过讨论时的处理方式

第二轮：
- 重写 description：写清启用场景（含商单、删减、语音变稿），写清不用于什么，加了判断标准
- 第一步末尾提示作者“赶时间可以回‘直接整理’”，回应评审指出的多一轮来回的问题
- 商单规则加上发布环节提醒（合作标注或报备、效果数字留截图）
