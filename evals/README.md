# 测试用例

每个用例由一个没看过开发过程的独立 agent 运行：只给它 `SKILL.md`、`references/` 和用例输入，看输出是否符合下面的检查项。`*.output.md` 是实际运行结果，供对照。

另外还用一篇未公开的真实语音稿做过第一步测试（识别错误 30 处左右、三个中心抢位置），不放进仓库。

## 检查项

所有用例通用：
- [ ] 没有改写作者的句子，只调顺序、合并、修识别错误
- [ ] 没有编造经历、数据、例子，缺的地方用【】提示
- [ ] 没有把“吧”“大概”“我觉得”改成确定语气
- [ ] 没有破折号，没有金句收尾，没有加粗和小标题进成稿
- [ ] 第一步之后停下等作者，不擅自出成稿

## case-ad：商单稿

输入：品牌要求 90 秒内、15 秒内提到产品、不提竞品；稿子里点名了一个竞品，产品名在第 103 字才出现。

期望：
- [x] 只做第一步，不直接改稿
- [x] 指出产品名出现太晚，并算出删改哪几句后会落在第几秒（实测计算正确：全稿 239 字，产品名在第 103 字，删掉竞品那句后在第 69 字）
- [x] 指出竞品名必须处理，并提出保留痛点、去掉名字的办法
- [x] 提醒“五千涨到八千”这个效果数字要确认是真实测的，保留原话里的“吧”
- [x] 建议保留作者对产品的保留意见（“工具只是辅助”）

## case-skip-discussion：作者要求跳过讨论

输入：作者说“不用讨论，直接整理”。

期望：
- [x] 直接出成稿，不追问
- [x] 成稿最上面说明按哪个中心和顺序整理（这条是第一轮测试后补进 SKILL.md 的）
- [x] 保留口头禅和“大概是这个顺序吧”这类语气
- [x] 缺例子的地方用【】提示，没有替作者编

## 第一轮测试后的修改

- 待确认词分成“直接改的”和“拿不准的”两组：真实长稿里列了近 30 条，作者很难看出哪些必须确认。
- 补上“作者要求跳过讨论”的处理方式：原版没写，agent 是自己判断的。
