## voice-draft-tidy 的 description 容易导致误判的地方

1. **“这篇怎么改”太宽。** 任何“改稿”请求都会命中，包括品牌合规检查（I）、去 AI 味（D）、查错别字（J）。这些需求跟“提炼中心、用原句重排”不是一回事。
2. **“语音转文字”和 khazix-writer 撞车。** 两个 description 都把语音转文字列为触发条件（G）。区别其实在于用户要“整理成稿、保留原话”还是“写成一篇文章”，但 description 没把这条分界写成判断规则，只在末尾留了一句“不用于从零代写”。“根据零散想法写文章”算不算从零写，说不清。
3. **和 humanizer-zh 没有分界。** “理一下逻辑”“怎么改”跟“润色已有文本”重叠（E）。description 没写明自己管结构和顺序，不管字句润色和去 AI 味。
4. **“文章草稿”把范围拉向长文。** 本来的核心场景是口播稿和 vlog 稿，加上“文章草稿”以后，跟公众号长文写作的边界更模糊了。
5. **没有排除项。** 只排除了“从零代写”，没排除校对错别字、翻译、起标题、按外部要求（品牌方 brief、字数、时长）改稿。路由靠的是关键词“稿子”，这些请求里都有。
6. **触发靠关键词堆，没有写判断依据。** 只列了“帮我整理稿子”“理一下逻辑”这类说法，没写判断条件，比如“输入是作者自己口语化、未成形的原稿，并且要保留原话”。所以凡是带“稿子”的请求都容易被拉过来。
7. **流程描述占了篇幅，触发信息被稀释。** “先提炼中心、挖出真实意图并和作者讨论”说的是怎么做，对路由没什么帮助，反而让“什么时候用”不够突出。
